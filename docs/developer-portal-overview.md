# Developer Portal (Frontend) Overview

`docker/portal/` is a static, vanilla-JS/HTML/CSS dashboard served by the `nginx` container at
`http://localhost` (root path `/`). It has no build step, no framework, and no bundler — it's
served as-is from `docker/nginx/nginx.conf`'s `location /` block. **Always open it through
nginx at `http://localhost`**; opening `index.html` as a file does not work (see below).

## Structure

```text
docker/portal/
├── index.html              # Shell page; assembles partials via Nginx SSI
├── thumbnail.jpg            # Favicon / brand image
├── css/style.css            # All styling
├── js/
│   ├── app.js                # Tab switching, toasts, modals, LocalStack health modal
│   └── aws.js                # One fetch/render/submit function set per AWS service
└── partials/
    ├── header.html            # Top nav + tab switcher (Platform / AWS)
    ├── overview.html          # "Core Platform Services" tab — static cards for each Docker service
    ├── aws-services.html      # "AWS Services" tab — live LocalStack explorer (S3, SQS, DynamoDB, Secrets, Lambda, EventBridge, Kinesis)
    └── modals.html            # Shared modal dialogs used by aws.js (create queue, edit item, invoke lambda, etc.)
```

## How the page is assembled: Nginx SSI

`index.html` doesn't contain the actual card markup — it pulls partials in via **Nginx
Server-Side Includes** (`ssi on;` in `nginx.conf`, `<!--# include file="..." -->` directives).
This only works when the page is served *through Nginx* (`http://localhost`, port 80 by default,
`GATEWAY_PORT` in `.env`).

The portal depends on that nginx route in two ways, so opening `docker/portal/index.html` as a
file (`file://`) leaves it broken:
- Without SSI the includes are inert HTML comments and `.container` renders empty. `app.js`'s
  `checkAndLoadPartialFallback()` then tries to `fetch()` the four partials, but from absolute
  `/partials/...` paths, which don't resolve from a file (and browsers block `fetch()` on
  `file://` pages anyway).
- Every API call uses an absolute `/api/...` path, which only works because nginx rewrites
  `/api/` and proxies it to `api:8000`. Nothing answers those paths outside nginx.

## Two tabs, two different data sources

- **"Core Platform Services" tab** (`overview.html`) is entirely static markup — one card per
  Docker service (Swagger, pgAdmin, Redis Commander, Mailpit, Grafana, Prometheus, Locust) with
  hardcoded ports/links/credentials and a copy-to-clipboard PowerShell cheatsheet. It does not
  call any API.
- **"AWS Services" tab** (`aws-services.html` + `js/aws.js`) is a live console. Switching to it
  triggers `setPortalTab('aws')` in `app.js`, which calls a fetch function for every service
  (`refreshAwsStatus`, `fetchS3Objects`, `fetchSQSQueues`, `fetchDynamoTables`, `fetchSecrets`,
  `fetchLambdaFunctions`, `fetchEventBuses`, `fetchKinesisStreams`). Every one of these — and
  every create/delete/submit action alongside them — calls the FastAPI backend through the `/api/`
  path, which Nginx rewrites and proxies to `api:8000` (see `nginx.conf`).

`js/aws.js` mirrors the backend's `/aws` router almost 1:1: for each service there's a
`fetch*` (list), `openCreate*Modal`/`submit*` (create), and usually a `delete*` — the same pattern
described in [Adding a New AWS Service](adding-a-new-aws-service.md#the-pattern). If you add a new
backend AWS integration and want it in the portal, you'd add the matching trio of functions here
plus a card block in `aws-services.html` and a modal in `modals.html` — none of this is generated
from the OpenAPI schema.

## The LocalStack health-check CORS workaround

`app.js`'s `openHealthJsonModal()` calls `/api/aws/health-raw` instead of hitting LocalStack's
`/_localstack/health` endpoint directly from the browser. The comment in the code explains why:
LocalStack's health response lacks an `Access-Control-Allow-Origin` header, so a direct
browser-to-LocalStack fetch is blocked by CORS even though the request itself succeeds. The
backend's `GET /aws/health-raw` endpoint (`app/api/v1/endpoints/aws.py`) exists specifically to
proxy that call server-side and sidestep the browser CORS restriction. If it fails, the modal
falls back to the already-CORS-safe `/api/aws/status` endpoint.

## Related: the dedicated S3 Browser (Sairo) container

Separately from the portal's own S3 tab, `compose.yml` also runs a third-party S3 browser
(`s3-browser`, image `stephenjr002/sairo`) on port 8085 with its own login. It mounts
`docker/s3-browser/sitecustomize.py`, which monkey-patches `botocore.signers.RequestSigner` so
that presigned URLs generated inside the container (pointing at `http://localstack:4566`) get
rewritten to `http://localhost:4566` before being handed to your browser — otherwise download
links generated by Sairo would 404 outside the Docker network. This has nothing to do with the
`docker/portal` frontend, but it's part of the same "S3 in a browser" surface area.
